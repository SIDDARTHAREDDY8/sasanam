Source: public web search + one page open by the wave-69 coordinator subagent

No local changes were made by this research; everything below is intake for

## L1. Known-default HMAC key → full token forgery (real, Sep 2026)

**JFrog Artifactory CVE-2026-82329 (CVSS 9.8).** The cluster-join endpoint
accepted a JWT whose HMAC secret was, on default installs, "a blank 32-byte
value that any network-adjacent attacker can predict". One forged POST
returned a fully-scoped administrator token with zero credentials. JFrog's
advisory says the secret "was not cryptographically randomized on first
startup" in vulnerable versions; the fix generates a random join key at
initialization. Campaign ran Aug 15 → Sep 8, 2026; 49% of exposed instances
still unpatched two weeks after fixes shipped (Wiz).

Two facts matter for this repo's key management:

1. **Patch ≠ rotation.** JFrog confirmed the upgrade "does not revoke admin
   tokens already minted by attackers and does not rotate a cluster join key
   already captured". Rotation of existing material is a separate, explicit,
   operational step — exactly why `keys.record_rotation()` exists and why
   dev-era chains are never silently re-signed in our design.
2. A predictable HMAC secret collapses the *entire* trust story of the audit
   log, not just one endpoint. This is the real-world analogue of the F73/F29
   residual: with the public dev key, our dev-era chains are forgeable by
   anyone who read the docs. Wave-69's explicit `GOV_DEPLOYMENT_MODE` guard
   and the production/dev contradiction refusal are the structural version of
   JFrog's "randomized on first startup" fix — never fall back to a
   predictable key in production.

URL (verbatim from search): https://www.decryptiondigest.com/blog/jfrog-artifactory-cve-2026-82329-supply-chain-backdoor

## L2. Trusting an attacker-supplied key at verify time (Authlib, 2026)

**Authlib CVE-2026-27962 (CVSS 9.1):** passing `key=None` to a verification
function made the library "trust and use a cryptographic key provided by the
attacker within the token itself" — attacker signs with their own key, embeds
the matching public key in the header, server accepts.

Direct analogue to the wave-69 key-confusion surface: verify must take its key
from *deployment configuration*, never from the artifact being verified.
Our posture: `verify_chain` binds `(epoch, prev_hash, content)` per MAC, and
era labels on entries are checked against the configured epoch (F32). The
w69 probes `key_confusion_dev_to_prod` / `prod_to_dev` encode exactly this.

URL (verbatim from search): https://securityonline.info/broken-keys-critical-authlib-flaws-jwt-forgery-padding-oracles/

## L3. The F73 pattern in the wild, fixed fail-closed

**bazspark commit** `c709f2ca9f34d801badcae6e305119dcb068aabe`: `fireai/core/qomn_self_healing_engine.py`
had a hardcoded `b'QOMN_SECRET_KEY'` fallback for its audit-log HMAC key when
`pytest` was importable in `sys.modules`. The fix removed the branch entirely
and RAISEs `SecurityError` in production (`FIREAI_ENV=production`) when the
real secret is missing — fail closed, no fallback.

This is the same shape as our pre-wave-69 F73 strict resolver
(env + in-code double opt-in, no-key refuses). Validation that the "refuse
loudly, no silent fallback" posture is the industry fix direction.

URL (verbatim from search): https://github.com/ahmdelbaz28-ux/bazspark/commit/c709f2ca9f34d801badcae6e305119dcb068aabe

## L4. Envelope-encryption best practices, 2026 (cloud world)

Recurring guidance across AWS KMS docs and 2026 practitioner guides:

- Key hierarchy: root (HSM) > KEK > DEK. Compromise of one DEK doesn't
  expose the root.
- **Key versioning:** keep old key versions available for decryption, use
  only the latest for encryption; migrate data progressively. This is exactly
  our `KeyRing` epoch model (retired epochs retained, active epoch signs).
- Rotate DEKs ~90 days, KEKs annually; automate; document the compromise
  rotation procedure *before* you need it.
- Zeroize plaintext DEKs from memory after use (cryptoserve uses `zeroize`;
  AWS guides say discard plaintext data key immediately after encrypt/decrypt).
- Log KMS operations for audit (who accessed what, when).

**Gap worth future waves:** we do *not* zeroize in-memory key material
(`resolve_active_key` returns raw bytes; nothing wipes them). Candidate for a
future finding/wave, along with per-context DEKs. Not this wave — our KMS
provider is the test-local `FakeKmsProvider`, and $0/local constraints hold.

## L5. Chancery security assessment (2026-07-10) — guard completeness

An assessment of an app config guard that rejected exact insecure defaults
found it only matched the *exact* string (weak-but-different passes) and only
covered first-boot. Lesson applied in wave-69: our guards deny-list the *dev
byte value and the dev epoch* on configured paths and deny-list the
*contradiction condition* (production + both opt-ins), not just exact env
strings — but the Chancery note is a reminder that deny-lists need
completeness reviews. Worth a future audit pass: enumerate every path by which
the dev bytes can reach `hmac.new` in `gov/`.

URL (verbatim from search): https://github.com/guidorugo/chancery/blob/HEAD/SECURITY_ASSESSMENT_10-07-26.md

## What this wave takes from the research (recorded, not re-scoped)

- Wave-69's explicit deployment-mode guard + production contradiction refusal
  is aligned with how the industry is fixing this class of bug (fail closed,
  random-by-default, explicit rotation).
- The JFrog "patch ≠ rotation" point is now written into
  `KEY_MANAGEMENT_DESIGN.md`'s rationale: rotation must be explicit, and
  previously-signed material under a captured key must be treated as suspect
  (we chose "never silently re-sign; dev era = consistency only").
- Zeroization + full deny-list-completeness audit are recorded as candidate
  future-wave work, NOT this wave.
