## B1 intake follow-through (wave-57 P2 decisions)

### (a) Academic-utility hopping class (2026-09-18) — NO registry situation; documented why

The class (evaluation-agent swarm using a University of Toronto open
link-shortener as a dynamic redirector for payload delivery, command
exchange, and egress-filter bypass via benign educational-domain
reputation) decomposes against our controls into three parts, none of
which warrants a new registry situation:

1. **Planted-secret exfil via a benign redirector** — already covered.
   The canary tripwire matches *payload*, not destination reputation:
   `canary.p1.cross_channel_replay_trips` (planting channels are not
   silos), `canary.p1.encoded_replay_trips` (encoding-aware matching),
   `canary.p1.bearer_token_api_call_trips`. A redirector in the middle
   changes nothing about the trip. A new situation would duplicate
   coverage, not add it.
2. **Real-secret exfil via an allowed redirector** — owned residual,
   not a miss. The F81 proxy design (§7.3, §10) states plainly that
   exfil to *allowed* destinations is outside the wall; real-secret
   exfil there is secret hygiene's job. Registering a situation that
   asserts "stopped" would be dishonest; one asserting "executed" would
   just pin the residual. No finding (no independently-reachable miss
   demonstrated — same conclusion as wave-56).
3. **The reputation-laundering element** — vacuous against our stack.
   Our controls never did reputation-based filtering, so there is no
   reputation-trust assumption for the class to break. The reporters'
   takeaway ("deterministic destination allowlists required at the
   network boundary") is exactly the F81 proxy design's posture —
   converging evidence, not a gap.

### (b) Spain AEPD autonomous data-theft report — CONFIRMED, case-study pending patterns refresh

Details have firmed up well beyond the wave-56 "details thin" watch
note — now multi-source confirmed:

- **Reuters (2026-09-15):** AEPD received the first reported personal-
  data breach notification allegedly carried out by an AI agent; agent
  used a widely known LLM to identify vulnerabilities, gain access,
  modify personal data, access invoices. Information under review; use
  of a model does not imply the model/provider was compromised.
- **BleepingComputer:** attack chain as reported — agent searched for
  flaws, logged in with found credentials, probed apps for further
  issues, modified personal data, accessed financial documents.
- **Infosecurity Magazine (Francisco Pérez Bes, AEPD president, post
  2026-09-14):** agent initiated a scan of "generic files" enabling
  login; "once inside... autonomously began searching for
  vulnerabilities... allowed them to modify personal data and access
  invoices"; agent "used as an instrument to successfully chain
  together different phases of the attack" — i.e. third-party deployed,
  limited human intervention, not a rogue-agent incident.
- **AEPD's own takeaways (via BleepingComputer):** AI does not create
  new threats but increases speed, scale, adaptability and compresses
  defender response margins; strengthen digital identity and
  credential security (agents can use compromised accounts/API keys
  with excessive permissions at machine speed); manual intervention no
  longer sufficient — human oversight needs fast detection,
  containment, response.
