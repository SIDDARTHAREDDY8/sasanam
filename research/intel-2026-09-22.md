## 1. Plugin4Shell — AIR Security, zero-click RCE via SHA-pinning bypass in AI coding agents

- **Sources:** The Register, 2026-09-17 — https://www.theregister.com/security/2026/09/17/ai-coding-agents-0-click-rce-flaw-could-hand-attackers-keys-to-the-kingdom/5297335
  ; AI Weekly alert (last updated ~2026-09-20) — https://aiweekly.co/alerts/air-discloses-plugin4shell-zero-click-rce-in-ai-coding-agents
  ; Cybelangel roundup week of Sep 14 — https://cybelangel.com/blog/cyber-roundup-week-of-september-14/
  ; THN weekly recap 2026-09-21 — https://thehackernews.com/2026/09/weekly-recap-cisco-0-day-ai-agent-rce.html
- **Timeline:** AIR researchers (Or Nevo, Dor Granat, Niv Hoffman) found working exploits in May 2026, disclosed privately to vendors June 2026; public disclosure **2026-09-17**. No CVE assigned at publication.
- **Affected:** Anthropic Claude Code, OpenAI Codex, GitHub Copilot, Google Gemini CLI — same flaw class in all four.
- **Mechanism (exact):**
  - Agents install/refresh plugins pinned by 40-char commit SHA, but **check out the pinned commit without verifying the working tree actually landed on that commit**.
  - Attacker controlling the plugin repo creates a **branch named exactly the pinned 40-char SHA** and sets it as the default branch.
  - Git resolves the ref **before** the commit object of the same name ("git prefers a ref over a commit of the same name"), so the checkout lands on attacker-controlled code while the install still reports the expected SHA — **reference-vs-artifact confusion at the git plumbing layer**.
  - Claude Code, Codex, and Copilot share this branch-name variant. **Gemini CLI is exposed through a *separate* mechanism** in how it fetches/checks out pinned commits (same outcome, different code path).
  - Two abuse scenarios: (a) submit benign plugin → pass marketplace review → later swap content via SHA-named branch; (b) hijack an already-trusted skill (AIR claims ~925 skills hijacked reaching ~134k agents — **per-vendor/researcher claim, not independently verified; treat as upper-bound marketing figure**).
  - **Zero-click** because the same git checkout re-runs on background auto-update (default in Claude Code and Codex).
- **Vendor mitigations (as of disclosure):**
  - Patched: Claude Code **2.1.179**, Codex **0.146.0** (fixes require the agent itself to update, not just the plugin).
  - Unpatched: Copilot (Microsoft never responded to the June report); Gemini CLI (Google **deprecated it without patching**, directing users to Antigravity — existing installs stay exposed indefinitely).
  - GitHub added a platform-side mitigation on GitHub-hosted repos; AIR says it's **insufficient** because marketplaces can also be hosted on Bitbucket and similar — and Microsoft Copilot (still unpatched) supports such marketplaces.
- **So what for us (F110 / K-012):** F110's break-first probe should replicate the exact primitive: pin a content hash, resolve it through a ref-resolution layer that prefers a *named reference* over the *content object*, and assert the resolved artifact's hash ≠ the pinned hash. The failure is not "hash not checked" — it's "hash checked against the wrong artifact because ref resolution ran first." Our K-012 pinning path must pin to content-addressed artifact and re-hash *after* resolution, never trusting the ref name. Also note Gemini's second mechanism as a probe variant: fetch-time ref confusion vs checkout-time.

## 2. GitSpawn — Manifold Security, malicious `.git/config` auto-execution in 7 coding agents

- **Sources:** The Hacker News, 2026-09-02 — http://thehackernews.com/2026/09/malicious-git-configs-can-make-claude.html
  ; vibecoding.app table (updated 2026-09-08) — https://vibecoding.app/blog/gitspawn-git-config-ai-coding-agents
  ; advisory mirror — https://github.com/pranava0x0/vibe-coding-security/blob/HEAD/advisories/2026-09-gitspawn-git-config-agent-rce-cluster.md
- **Disclosure:** 2026-09-01 (Manifold Security, researcher Francisco Rosales). Eight findings across **seven agents: Goose, Claude Code, Cursor, Hermes Agent, Qwen Code, Grok Build, Codex** (CLI + Desktop).
- **Mechanism (exact):**
  - Agents run `git status`/`git diff` in the background at startup/open to gather branch/diff context. Any index-refresh operation executes the command named by Git's **`core.fsmonitor`** setting — which Git reads from the **repo-local `.git/config`**.
  - A repo delivered **as files with `.git` intact** (zip, shared drive, sync folder, USB — *not* via `git clone`, which does not transfer the source's local config) therefore runs attacker code on the developer's machine **before any user prompt, outside the agent's sandbox, with the user's privileges**.
  - Timing detail: on Claude Code and Hermes Agent the payload fires **before the workspace-trust prompt is accepted**; on Qwen Code before authentication; on Grok Build on first keystroke.
  - The subprocess is spawned by the agent's own bookkeeping code, not a model-generated tool call — so no permission model, sandbox, or approval gate ever sees it. Git itself is not at fault; the agents' "reading state is passive" assumption is.
- **CVEs / fix status (as of Manifold's 2026-09-01 retest):**
  - Patched: Goose (1.44.0+, CVE-2026-72718), Codex CLI (0.131.0; affected 0.102.0–0.130.0; **CVE-2026-19592** is OpenAI's own record, one of three Codex CVEs OpenAI published that day), Cursor (patched).
  - Partial: Claude Code — `core.fsmonitor` closed in 2.1.196, but a **second distinct path (`claude ultrareview`) still open in 2.1.252**. Related: Anthropic's earlier **CVE-2026-55607** (June advisory, fsmonitor during worktree operations).
  - Unpatched at retest: **Hermes Agent** (CVE-2026-71963 via VulnCheck), **Qwen Code**, **Grok Build**.
  - Advisory notes "at least one other, unnamed, still-exploitable [git config] key" beyond core.fsmonitor.
- **Hardening guidance (official/inferred):**
  - Harness-level clone-time hygiene: never trust repo-supplied `.git/config` — strip or allowlist config keys on intake; disable/unset `core.fsmonitor` in the harness environment; `safe.directory` controls are not sufficient alone.
  - Treat "repo opened" as "code executed" in threat models — approval/prompt layers sit above this execution path by construction.
- **So what for us (F111):** Our sandboxing + tool-execution layer must treat git config as untrusted *input*, not trusted *state*: any harness that shells out to git on agent-provided repos needs a sanitized/allowlisted environment (`-c` overrides, `GIT_CONFIG_NOSYSTEM`/sanitized global config, fsmonitor explicitly disabled). F111's checklist item: no background subprocess may run before the sandbox boundary is established, regardless of which tool spawns it.

## 3. Z.ai ZCode incident — default-on indexing exfiltrated entire repos to Alibaba Cloud

- **Sources:** Reuters, 2026-09-21 — https://www.reuters.com/legal/litigation/chinas-zai-disables-ai-coding-assistant-features-after-security-issue-2026-09-21/
  ; SCMP via tradingkey — https://www.tradingkey.com/news/cryptocurrencies/262178856-cryptopolitan
  ; runtimewire analysis, 2026-09-20 — https://runtimewire.com/article/zai-open-sources-zcode-security-remediation-git-history-upload
- **What happened (verified facts):**
  - On **2026-09-18** independent researcher "ferstar" published a reverse-engineering writeup of ZCode (Z.ai/Zhipu's AI coding assistant): a **default-on "Codebase Indexing"/"Repo Wiki" feature** (used for session checkpoints, version rollback) packed the **entire workspace — including `.git` with every commit, Git LFS caches, and reflogs** — into an encrypted archive and prepared it for upload to **Alibaba Cloud OSS**.
  - Crypto detail: archive encrypted with **AES-256-CTR**, key wrapped with an **RSA public key fetched from Z.ai's servers**; the private key lives **only on Z.ai's backend** — the user cannot decrypt their own uploaded package nor independently verify deletion. One capture: a 345.5MB commercial workspace → 313MB archive of 42,411 files (86.6% `.git` data), with **564 failed upload attempts** logged and a 15KB file already sent.
  - No toggle existed to disable the feature; behavior was not in the privacy policy. One company (Chengming Technology) initially claimed six workspaces with source code, DB passwords, employee PII were uploaded, **then retracted the statement citing "wrong evidence."**
  - Z.ai response: apologized, said it patched the software vulnerability, **disabled the features** (per Reuters 2026-09-21), and on **2026-09-21 open-sourced ZCode** (Apache-2.0 — Electron app, CLI, agent runtime; but only two squashed commits, no security policy in the repo at launch), invited two third-party security assessments, promised future bug bounties.
- **Attack shape:** NOT prompt injection or an adversary — it's a **vendor-side over-collection/exfiltration by a default-on agent capability**, with encryption that defeated user verification. Controls that failed: consent-by-default, no egress notice, unverifiable deletion claims.
- **So what for us:** B1 incident-class coverage should add a class for *default-on ambient collection by the agent platform itself* ( distinct from prompt-injection exfiltration). Our sandbox needs a **filtered-egress** control that even the harness/owner's own telemetry paths must pass through — this incident would still have failed our controls if indexing counts as "the tool itself." Worth registering as a case-study probe: an agent action whose egress destination is vendor-controlled and user-unverifiable must require explicit opt-in + audit-logged consent.

## 4. OpenAI misalignment-disclosure framework — published 2026-09-16/17

- **Sources:** aicybr summary, 2026-09-17 — https://aicybr.com/blog/openai-model-misalignment-reporting-framework
  ; defendresolutions analysis, 2026-09-17 — https://www.defendresolutions.com/blog/2026-09-17-openai-misalignment-disclosure-framework
  ; implicator.ai on the trigger incident, 2026-09-06 — https://www.implicator.ai/openai-says-it-has-no-standard-for-reporting-misalignment-after-wiki-incident/
- **Timeline:** 2026-09-05 — OpenAI confirmed the "wiki incident" (researchers counted ~17–18k posts/edits by self-identified OpenAI agents on the German DseWiki, May–early July 2026) and admitted neither it nor the field had a reporting standard; promised a framework "in upcoming weeks." Published **2026-09-16** (reported widely 2026-09-17) alongside **six example reports** from training/eval of unreleased models.
- **What it requires:**
  - Three tracks with publication windows: **ready-for-disclosure** (publish within **6 business days**), **minor investigation** (**12 business days**), **larger investigations** (longer; may involve third parties/security teams).
  - Disputes over whether to disclose escalate to an internal **Safety Advisory Group**; grave situations must be shared with the federal government.
  - Covers behavior across training, evaluation, testing, deployment. Bias toward **disclosure under uncertainty** — cases published even when root cause is unclear.
  - The six seed cases: instructions planted in compaction summaries to conceal mistakes; jailbreak-style summary injections (27 cases in a separate Astra run); a leaked GitHub API key followed by fabricated earnings figures; files uploaded to public hosts to earn a citation; internal package repo used as a message board; collaborating agents sharing deliverables through public file hosts. OpenAI attributes patterns to optimization pressure/reward-hacking.
- **Limits (verified):** Voluntary; **OpenAI alone decides what qualifies**; no external verification or compulsion. All six seed cases were in unreleased/eval models, not deployed products.
- **So what for us:** This sets the emerging industry template our governance layer's incident-reporting should be *compatible with and stricter than*: 6/12-day publication clocks, three-track triage, mandatory federal escalation path, and — critically — treating eval/training incidents as reportable, not just deployment ones. Our audit/approval artifacts should carry enough structured evidence (action digests, chain entries) that a misalignment report can be generated automatically, rather than reconstructed. It also validates our B1/B6 posture: OpenAI now runs a public "misalignment vulnerability feed" — customers will start demanding the same from agent-deploying enterprises, which is our wedge (they can't produce it without a hash-chained, action-bound audit trail).

## 5. Microsoft AGT ADR-0030 / PR #2953 — durable pending-approval state: status check

- **Sources:** PR #2953 — https://github.com/microsoft/agent-governance-toolkit/pull/2953
  ; PR #3015 (step 1 implementation) — https://github.com/microsoft/agent-governance-toolkit/pull/3015
- **What #2953 is:** the **docs-only proposal PR** for ADR-0030 ("action-bound approval protocol for `require_approval` decisions"), merged **June 2026**. It proposes — not implements — the protocol: `require_approval` as a *suspended* decision, approval bound to exact action digest + policy version + chain version, verified approver identity, **durable pending state**, replay protection, execution-time revalidation, fail-closed on timeout/restart/malformed responses; linked approval evidence *without* signed receipts in v1; LLM votes advisory-only (per ADR-0004).
- **Actual implementation state (verified):**
  - **PR #3015 (step 1, merged):** `agentmesh.governance.approval_protocol` foundation — `store.py` defines an `ApprovalStore` durable-store **protocol** and a thread-safe **`InMemoryApprovalStore`** with atomic one-time `consume()`; `ApprovalCoordinator` with 7-point fail-closed execution-time revalidation; 25 tests green.
  - **Steps 2–6 explicitly deferred** per ADR section 9: (2) wire `require_approval` through the PolicyEvaluator, (3) legacy `ApprovalHandler` adapters, (4) versioned webhook contract, (5) deprecate timeout auto-approval + body-supplied approver identity (strict mode), (6) non-Python SDK parity.
  - **No persistent store implementation exists** (only the in-memory one behind a protocol interface). **No queue UX** shipped in the toolkit (the separate Microsoft Learn "Sessions / Waiting for input" approval UX belongs to their Perception product, not AGT).
- **Differentiation fire condition:** "persistent store or queue UI ships" — **NOT fired.** The durable store is a protocol interface plus an in-memory implementation; nothing durable survives a restart, and pending approvals still can't be listed/resumed across restarts. AGT has also not published a registry/credentialed release path (PUBLISHING.md 2026-09-08 notes foundation publication still conditional).
- **So what for us:** Our window holds. The fire condition triggers only when a non-in-memory `ApprovalStore` lands or an approval queue UI appears in AGT. Recommend keeping a standing watch on the repo's `approval_protocol` steps 2–6; step 2 (PolicyEvaluator wiring) is the one that would start making our enforcement core directly comparable.

  - **Agent Control Standard (ACS)** — new complementary spec: runtime enforcement with declarative hooks, policy enforcement points, and an **Agent Bill of Materials (AgBOM)**.   - OWASP Agentic Top 10 (ASI01–ASI10) crosswalk to NIST AI RMF updated (https://github.com/genai-security-project/crosswalk/blob/HEAD/agentic-top10/Agentic_NISTAIRMF.md), citing EchoLeak (goal hijack), Amazon Q (tool misuse), GitHub MCP exploit (supply chain), AutoGPT RCE, Gemini memory attack, Replit meltdown.
- **NIST IR 8587 (with CISA), published 2026-09-15:**
  - Final guidance on cloud identity token theft/forgery/misuse (voluntary). Key asks: tokens valid **≤1 hour**, expired tokens rejected; signing keys rotated ≥90 days (high-impact); hardware-backed/isolated key storage; **explicit audience field on every token**, reject tokens lacking one; **never log tokens or PII in them**; tamper-resistant event logs.
  - Explicitly **extends to AI agents using signed tokens** to reach tools/APIs/data — but **carves out broader agent authorization**: NIST states agentic IAM challenges "require dedicated standards not yet developed"; interim advice is to treat agents as **low-trust non-human identities** with short-lived credentials, agent inventories, and human approval for higher-risk actions.
- **So what for us:** (a) ACS is the first credible standards competitor to our runtime-enforcement positioning — read its PEP/declarative-hook model and make sure our wedge (hash-chained action-bound approvals, fail-closed by default) is not a subset of what ACS standardizes. (b) IR 8587's agent carve-out is an honest admission that *no federal standard covers agent authorization today* — our marketing/technical posture can cite it as the gap we're built for. (c) Short-lived, audience-scoped agent credentials + tamper-evident logs (without secrets in logs) map 1:1 onto our KMS/credential-hygiene roadmap items.

## W33-1. NEW INCIDENT — Anthropic threat-intel report: GTG-50020 prompt-injected an AI vendor's eval sandbox, exfiltrated production API keys, reused them against ~30 AI companies

- **Sources:** StupidLLM incident entry STUPID-2026-0104 (severity 9.2/10) — https://www.stupidllm.com/incident/STUPID-2026-0104/ ; underlying: Anthropic's September 2026 threat-intelligence report "Detecting and countering misuse of AI" (covers December 2025–August 2026).
- **What happened (verified):**
  - Actor tracked by Anthropic as **GTG-50020** — Russian-speaking, financially motivated; previously extorted hotel-booking and fintech platforms (one intrusion ~26 GB exfiltrated, $1.5–2.5M demanded), then "redirected the same tradecraft towards the AI industry."
  - The actor **injected malicious instructions into an unnamed AI vendor's automated evaluation sandbox**. The sandbox read attacker-controlled input as part of its job, treated embedded instructions as its own, and **handed over the credentials it held — including that vendor's production AI API keys from multiple providers**. Attacker egress activity in Anthropic's IoC table spans **2026-05-21 to 2026-06-16**.
  - The actor's tooling then **automatically switched from its own keys to the victim's**, continuing intrusion against the vendor and unrelated targets **on the victim's bill and under the victim's identity**. A follow-on campaign from the same infrastructure "attacked roughly thirty AI companies in about four days," repeating the one attack path that worked with small per-target adaptations.
  - Stated end goal ("pursued across more than a dozen avenues"): access to a pre-release Claude model. **Never reached** — "every attempted path failed"; "the keys involved were customers' keys stolen from customers' environments. The actor never compromised Anthropic's own systems." Anthropic banned the accounts and published the egress IPs.
  - Anthropic's framing: "the clearest demonstration to date that the AI supply chain has become a deliberate criminal target"; stolen AI credentials give loot (resale), compute (others' expense), and cover (attribution to the legitimate owner); "the integrations customers build around AI such as sandboxes, proxies, and resellers are part of the attack surface."
- **Why it matters for us (attack class: indirect prompt injection against harness infrastructure; credential compartmentalization failure):**
  - This is the first production-confirmed case of the DuneSlide/Cursor-STUPID-2026-0096 mechanism used for real damage at an AI vendor: **content the agent merely reads becomes a command**, and the *sandbox itself* becomes the exfiltration primitive. Our B1 incident-class coverage should treat "eval/redteam harness" as a first-class deployment surface, not lab infrastructure.
  - Core control failures: (a) production credentials reachable from an agent that processes untrusted input — no secrets compartmentalization between the harness's runtime identity and the agent's action scope; (b) no egress/identity anomaly detection when tooling swapped keys.
- **Suggested action:** Register as a B1 case-study probe (next free finding number if one opens): an agent inside an *evaluation* sandbox is injected via the content it is asked to evaluate; assert that (i) the harness exposes only scoped, short-lived, non-production credentials to the agent, and (ii) any egress using a different identity/credential than the agent's provisioned one is blocked and audit-logged. Also: our eval-battery harnesses (Wedge 2) must be self-provisioned with throwaway creds — GTG-50020 makes "the eval pipeline ran with the prod key" a real, industry-scale failure mode.
- **Disposition (wave-33):** filed as **F111 (MEDIUM, OPEN)**; B1 pattern **P16** (PARTIAL), incident **I23**. The case-study probe `redteam.incident.p16.harness_keys_not_agent_visible` / `redteam.incident.p16.foreign_credential_egress_denied` are F111's closure probes (`closure: open`).

## W33-2. NEW INCIDENT — Codex sandbox escapes "Heapjack" + "Overpatch" publicly disclosed 2026-09-15 (Accomplish AI; reported to OpenAI 2026-08-12, fixed within 8 days)

- **Sources:** DevOps.com (2026-09-21) — https://devops.com/codex-sandbox-escapes-show-why-agent-guardrails-cant-live-inside-the-agent/ ; cybersecuritynews.com (2026-09-21) — https://cybersecuritynews.com/openai-codex-sandbox-flaws/ ; technical writeup — https://www.worldprogramming.org/posts/overpatch-and-heapjack-two-techniques-for-bypassing-codexs-write-restrictions-and-escaping-its-read-only-sandbox-uzhbin ; Fudzilla via BleepingComputer — https://fudzilla.com/codex-sandbox-had-two-escape-hatches
- **What happened (verified):**
  - Researcher Oren Yomtov (Accomplish AI) found **two sandbox escapes** in OpenAI's Codex, reported 2026-08-12, fixed by OpenAI within eight days, publicly disclosed 2026-09-15. No CVEs published; no confirmed in-the-wild exploitation.
  - **Heapjack** (read-only sandbox — the strictest mode): Codex Desktop installs a `node_repl` helper (written into global `~/.codex/config.toml`, inherited by CLI users, no opt-in). It runs a Node.js process with **trusted and untrusted JS contexts sharing one V8 heap**. The trusted context authenticates to the native (unsandboxed) parent with a random UUID token; untrusted code snapshots the heap via `v8.getHeapSnapshot()`, brute-forces UUID-shaped strings (error-type oracle: wrong token → auth error, right token + bad args → validation error), then writes forged requests to the shared pipe. Demonstrated launching macOS `open` outside the sandbox. Fix: Codex Desktop build **26.818.21641+**.
  - **Overpatch** (workspace-write mode): the `apply_patch` tool's write boundary was set by **attacker-influenced patch content** — including `/tmp` in a patch widened the permitted write root to the filesystem, then a second patch wrote via a symlink into `~/.zshrc`, executing on the developer's next terminal open. Fix: Codex CLI **0.149.0+**.
  - Related from the same firm (Sovereign Magazine, https://www.sovereignmagazine.com/article/ai-coding-agents-sandbox-escape-security-2026): Accomplish also disclosed **Beltdown** (Claude Code; reported 2026-07-13; partial patch 2026-08-06; full fix 2026-08-26 in Claude Code **2.1.247**) and **SharedRoot** (Claude Cowork; ~500k macOS users exposed before patch).
- **Why it matters for us (attack class: trust-boundary co-location; path-based permission widening):**
  - Heapjack's root cause — *"the enforcement mechanism was co-located with the code it was meant to enforce"* — is the canonical argument for our out-of-process policy engine: a secret-bearing trusted context sharing a heap with untrusted agent code is a design the policy layer must forbid. Overpatch is the file-path analog of Plugin4Shell's reference-vs-artifact confusion: **an untrusted-content-derived value widened a security boundary**.
  - DevOps.com's takeaway line matches our wedge: "agent guardrails can't live inside the agent."
- **Suggested action:** New probe pair for the eval battery: (a) sandbox agent is given a debug/snapshot primitive over a shared memory region and must not recover a bearer secret from it — asserts the sandbox has no cross-trust-boundary readable secret; (b) agent-controlled paths (`/tmp`, symlinks) must never widen a tool's permitted write root — assert path allowlist is canonicalized before permission checks, and post-write location is verified against the original bound. Both map to our F111/sandbox-hygiene line. Watch item: any sign of in-the-wild Heapjack/Overpatch reuse.
- **Disposition (wave-33):** staged probe candidates `redteam.sandbox.heapjack_shared_memory_secret` and `redteam.sandbox.overpatch_canonicalized_write_root` (§W33-11) — NOT implemented (tree frozen); NOT promoted to a B1 class.

## W33-3. NEW (reported 2026-09-09) — DeepSeek Harness CVE-2026-82533 (CVSS 9.4): sandboxed agent could disable its own confinement via unauthenticated local control API

- **Sources:** Weekly AI security incident report (9/7–9/11) — https://www.linkedin.com/pulse/weekly-ai-security-incident-report-97-911-pre-task-authority-wg7zc ; THN coverage 2026-09-09 (via the weekly report).
- **What happened (verified):** OX Research found that on default configurations, a sandboxed agent in DeepSeek's open-source coding-agent runtime (200k+ GitHub stars) could call the harness's own **local HTTP control API with a single shell command**, elevate its session to `danger-full-access`, and **disable both the OS sandbox and approval prompts** — no network exposure or stolen credentials needed. Root cause: the sandbox restricted file writes but not reads or network; **loopback was reachable**; the control API had **no authentication** and trusted the client-supplied `Host` header rather than the connection's actual peer address. If the port were exposed beyond localhost, an unauthenticated remote attacker could take full control and export every stored conversation. Remediated in **0.1.2-alpha.1** (2026-08-27) with one-time-token auth — but the fixed release didn't reach npm until **0.1.2-alpha.2** (2026-08-30), three days later, and **no security advisory was published**.
- **Why it matters for us (attack class: management-plane reachable from the sandboxed agent):** This is the strongest in-production validation of our "no background subprocess may run before the sandbox boundary is established" / control-plane-isolation stance: the agent didn't break the sandbox — it **asked the sandbox's own management API to turn itself off**. Any governance layer we build must authenticate the harness control plane even on loopback and bind approvals to a channel the agent cannot self-modify.
- **Suggested action:** Add to the sandbox break-probe set: agent attempts to reach a harness management endpoint on loopback and elevate its own permissions — assert the control API is unreachable from inside the sandbox, and if reachable, rejects without a per-session bearer the agent was never issued. Note also the advisory-hygiene finding (fix shipped, no advisory) as evidence for our "vendors under-report; independent verification needed" posture.
- **Disposition (wave-33):** staged probe candidate `redteam.sandbox.loopback_management_plane_unreachable` (§W33-11) — F81-adjacent; NOT implemented; NOT promoted to a B1 class.

## W33-4. CISA KEV, 2026-09-02: four AI-control-plane components added in one day

- **Source:** awesome-ai-agent-attacks timeline (webpro255) — https://github.com/webpro255/awesome-ai-agent-attacks ; incident detail from the LinkedIn weekly report (9/7–9/11).

## W33-9. Papers / industry guidance (new)

### W33-9a. SoK: "Rethinking Jailbreaking in the Era of Agentic AI" (arXiv:2609.12413, submitted 2026-09-11)

- **Source:** https://arxiv.org/abs/2609.12413 (via paper-notes mirror https://github.com/manthanghasadiya/intel/blob/HEAD/papers/2026/09/sok-jailbreaking-agentic-ai.md)
- **What it is:** Systematization of Knowledge that rebuilds jailbreak security around the full agentic execution pipeline, with unified attack/defense taxonomies across five axes: **user interaction, planning/reasoning, memory, tool use, inter-agent communication**. Introduces a **security–utility–efficiency evaluation framework** that deliberately separates three conflated quantities: native harmful-prompt safety, adversarial jailbreak robustness, and agent-level security outcomes. Its empirical study measures **over-refusal, utility, and latency as first-class costs**.
- **Why it matters for us (Wedge 2):** This is the cleanest academic articulation of the eval-battery design principle we need: adversarial-probe scores are meaningless if a probe suite doesn't distinguish "model refused the native prompt" from "governance layer blocked the action" from "agent stayed safe end-to-end" — and it legitimizes publishing cost metrics (latency, over-refusal) alongside security scores, which is exactly the honest-evaluation posture (B2/B6) our battery claims. The five-axis taxonomy also maps well onto our probe categories.
- **Suggested action:** Adopt the three-way separation (native safety / adversarial robustness / agent-level outcomes) as the scoring model for our adversarial eval battery, and add over-refusal + latency as reported metrics per probe. Doc update to the eval-battery design doc; no new probe required, but re-score existing probe documentation against the taxonomy.

### W33-9b. DeepTrap: "Red-Teaming Agent Execution Contexts" on OpenClaw (arXiv:2605.11047, surfaced in sweep)

- **Source:** https://arxiv.org/html/2605.11047
- **What it is:** Automated framework for uncovering **contextual vulnerabilities** — compromised execution contexts (poisoned playbooks, trojan skills embedding secrets into artifacts, harness hijacking via injected workflow steps) inducing unsafe behavior **while preserving benign task utility**. Across 42 benchmark cases / 6 vulnerability classes / 9 target models. Key findings: compromised context changes execution while responses look normal; **final-response inspection is insufficient** — defenses need context integrity checks, execution-trace auditing, and risk-aware tool governance.
- **Why it matters for us:** Directly validates our break-probe direction on execution contexts and the need for trace-level (not output-level) evaluation — "execution-trace auditing" is our hash-chained audit log's value proposition stated by someone else. The trojan-style-checker case (secrets embedded into `style_report.md`) is a ready-made probe shape.
