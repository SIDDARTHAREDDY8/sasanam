## 1. Atlassian Rovo exfil — PRIMARY-SOURCE VERIFIED (2026-09-22 re-check), filed as incidents I24/I25

**Primary sources (verified directly 2026-09-22):**
- PromptArmor original disclosure, published 2026-08-05: zero-click
  indirect prompt injection. Hidden instructions in an uploaded file
  cause Rovo to search Jira/Confluence, append the retrieved data to
  an attacker-controlled URL, and exfiltrate via Rovo's URL-retrieval
  tool: "there are no protections against opening a URL that has been
  dynamically created by the agent." Disabling web search org-wide
  does **not** stop it — "the web search setting fails to remove the
  tool for opening the search results." Disclosed 2026-05-23, case
  number 2026-05-25, follow-ups 2026-06-04 and 2026-07-29; still
  vulnerable at publication. Precision correction 2026-09-22: the
  Markdown-image rendering channel is described in the primary as a
  "well-known vector" with examples from PromptArmor's *other*
  research — PromptArmor does NOT demonstrate a complete Rovo attack
  chain through it. Our incident filing treats the Markdown-image
  channel as asserted-but-not-fully-demonstrated (unchanged P13
  disposition).
  https://www.promptarmor.com/resources/atlassian-rovo-exfiltrates-data
- Varonis Threat Labs original "RovoBlast" write-up (published
  2026-08-07, debuted at DEF CON 34): `rovoChatPrompt` URL parameter
  pre-fills chat entry — Parameter-to-Prompt into the victim's
  authenticated session, no jailbreak/permission-bypass, no
  warnings; ResearchAgent as the exfil chain ("push it to the public
  web as part of its 'research'"); disclosed via Bugcrowd, fixed
  server-side (Bugcrowd P2, $6,000 bounty, fixed 2026-07-08).
  https://www.varonis.com/blog/rovoblast
- Atlassian community write-up: both paths, no CVE; PromptArmor path
  remediation still unconfirmed publicly.
  https://community.atlassian.com/forums/Rovo-articles/Two-prompt-injection-paths-into-Rovo-one-fixed-RovoBlast-one/ba-p/3282296

**Disposition — filed as B1 incidents I24 (PromptArmor) and I25
(RovoBlast):**
- I24 Markdown-image channel → P13. Payload side FULL (P1 close-outs +
  F116 closure + RT10 G ratchets now pin the renderer-output shapes);
  renderer side stays the documented design boundary → **P13 stays
  PARTIAL**. Rovo is the second production incident (after EchoLeak)
  proving the reference filter's shape class is live.
- I24 URL-retrieval-tool channel → P1. This is the same
  injection-drives-exfil pattern as the staged P1 close-out
  (`redteam.incident.p1.injection_driven_exfil_denied`): injected
  instruction causes data to leave for an unallowlisted destination,
  denied by the egress allowlist (C-03). **P1 stays FULL.**
- I25 (crafted-URL chat preload) → P1/P6 boundary; covered by the same
  untrusted-influence egress denial. No new class.
- **Design lesson recorded (this is the novel contribution):**
  PromptArmor's decisive detail is that the *administrative toggle*
  (disable web search) did not govern the *exfil capability* (URL
  retrieval tool). Capability-level gating, not feature-toggle gating.
  Our layer gates at the capability level by construction: the egress
  allowlist binds the tool call's destination, not a UI toggle. Added
  to the wave-42 note in `workstreams/evals/INCIDENT_COVERAGE.md` (P1,
  P13).
- No new probe: the Markdown-image shapes are pinned by
  `redteam.rt9.f116_output_filter_bypass` + the 11 wave-42 RT10 ratchets
  (G); the URL-retrieval shape is pinned by the P1 close-out probes.
  Registering a duplicate probe would be B4-hygiene debt.

## 3. China AI Safety Governance Framework 3.0 — CORROBORATED (honest downgrade from "VERIFIED"), filed as B3 crosswalk

**Verification state (2026-09-22 re-check):** TC260 published v3.0 on
2026-09-14 (2026 National Cybersecurity Week opening, under CAC
guidance; previous versions 2024/2025) — corroborated by multiple
independent outlets: Radar Digital (2026-09-14), IAPP Asia-Pacific
notes, Trivium China, The Register, Xinhua/CGTN. Consistent reporting:
first version to formally codify autonomous-agent risks; principle of
ultimate human control (termination switches); agent-lifecycle
annex. The official TC260 PDF itself was **not** directly fetched —
treated as strong multi-source corroboration, not primary-source
verification.
- Radar Digital 2026-09-14: Framework 3.0 presented by TC260 at the
  2026 National Cybersecurity Week opening, under CAC guidance;
  expands agent treatment; principle that critical decisions remain
  under human control; risk-classification structure retained.
  https://www.radardigital.ai/en/articles/china-publishes-ai-safety-governance-framework-3-0-with-focus-on-agents-and-huma/
- NYU RITS summary of the May 2026 Implementation Opinions (CAC/NDRC/
  MIIT): three decision tiers (user-only / user-authorized /
  agent-autonomous); users retain final decision-making authority;
  developers must build detect/intervene/recover mechanisms.
  https://rits.shanghai.nyu.edu/ai/china-issues-first-national-policy-framework-dedicated-to-ai-agents/
- AI Safety China substack (TC260 March 2026 report, Table 1.2):
  Threat 9 (human oversight & traceability → full-lifecycle logging,
  log encryption & signing), Threat 10 (memory manipulation → memory
  verification, session isolation), Threat 11 (tool abuse → fine-grained
  dynamic access control, action scope constraints).

**Disposition — filed in `docs/STANDARDS_MAPPING.md`** alongside KISA.
Honest notes: the framework is a technical reference, not binding
law; the mandatory layer is the announced national standards
(recommended agent spec Jan 2026, mandatory application requirements
Apr 2026 — tracked, not claimed). Mapping: human final authority +
3-tier boundaries → C-05/C-06/C-07 GREEN; full-lifecycle logging +
signing → C-08 GREEN; tool-abuse controls → C-01/C-02 GREEN; memory
threats → C-13 AMBER (partial taint tracking); loss-of-control /
shutdown-resistance naming → demand-side signal for B1 corpus,
recorded in the differentiation watch list.

## 4. DigiCert AI Trust Manager (GA) — VERIFIED, filed as differentiation input

**Source:** DigiCert press release 2026-09-15 (GA, part of DigiCert
ONE): AI Passport — portable cryptographically signed agent
credential binding identity to an accountable owner; policy-based
"visas" defining which systems/data/actions the agent may access and
for how long; kill-switch revocation. July 2026 survey of 1,001 IT/
cybersecurity leaders: 78% experienced an AI-related incident in the
prior year.
https://www.digicert.com/news/every-ai-agent-needs-a-kill-switch-digicert-launches-ai-trust-manager

**Disposition — filed in `research/differentiation-strategy.md`**
(watch list, "not trigger" entry, wave-42):
- DigiCert does **credential issuance** (who the agent is, who owns
  it, what it's authorized to do). We do **runtime enforcement of
  what the credentialed agent does** (policy engine, approval queues,
  egress allowlist, DLP) + **hash-chained audit of what it did**.
  These are complements, not substitutes: a passport answers
  "should this agent exist and be trusted here"; our layer answers
  "did it stay inside its grant, and can we prove it."
- The passport model has a known failure mode we should name, not
  exploit: a valid passport with an overly broad visa is the
  confused-deputy problem with better paperwork. Our C-14
  (owner-minted, scoped, TTL-bound delegation grants) is the runtime
  half of that visa. Interop posture: our layer could consume a
  passport as the identity input to C-21/C-14 without issuing one —
  we stop at issuance (stop duplicating).
- Not a wedge threat: no enforcement-layer battery, no approval
  queue, no audit chain. Kill-switch headline ≠ our C-05/C-12 story;
  their kill switch revokes the credential, ours stops the run.
  Different layers.
