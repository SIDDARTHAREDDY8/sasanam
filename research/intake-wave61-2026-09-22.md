## 1. neoruntime: a real project documenting fail-open seccomp load (differentiation evidence)

camthink-ai/neoruntime (edge AI platform, Hailo) documents its
seccomp profile flow honestly, including this (opened page, "Current
Implementation Status" §3):

> **Failure behavior is fail-open at load time**: if
> `loadSeccompProfile` errors, the container is started **without**
> seccomp and a warning is logged (`runtime.go:384,497`).

And under "Next steps":

> Consider a fail-closed policy if a seccomp profile should be
> mandatory (load failures currently warn and start the container
> without seccomp).

This is the exact fail-open seam class wave-61's guard kills on our
side (our `_harden_worker`: `require_seccomp` → `_exit(127)` before
exec; the new guard: contradictory tier config → `SandboxError`,
no launch). A shipped, documented project still runs warn-and-
continue. No finding (not our code), but it is concrete external
validation of two things: (a) the fail-open-at-load seam is a real,
recurring industry shape, not a strawman; (b) our fail-closed
posture is a genuine differentiator — "we refuse; they warn."
Relevant to F81's wall-readiness story and the founder memo's
"sell evidence, not the engine" bet: the evidence artifact here
would be the refusal record.

## 3. CVE-2026-31431 "Copy Fail" (kernel crypto AF_ALG + splice container escape, disclosed 2026-05-01)

From search snippet (the-devops-daily writeup): kernel in-place AEAD
optimization + AF_ALG userspace crypto API + `splice()` race →
deterministic 4-byte page-cache write, demonstrated as container
escape via corrupted shared `/usr/sbin/ipset` executed by kube-proxy.
Patch: mainline `a664bf3d603d`; mitigation includes "drop a custom
seccomp profile blocking AF_ALG".

Boundary note, not a finding: kernel exploits are outside this
layer's threat model (established wave-59 for CVE-2026-64564/SCTP).
Our cage profile constrains `socket()` domains to {AF_UNIX, AF_INET}
→ an AF_ALG socket attempt dies at the errno tier (EPERM), same as
the SCTP shape. The incident reinforces the F81 wall-readiness D2
lane (kernel-load the exact filter in privileged CI) — the profile
is only as good as its loaded bytes.

## 4. macOS sandbox escape via `__OSINSTALL_ENVIRONMENT` (env var as security signal)

From search snippet (securityaffairs.com): `+[TTApplication
isRunningInInstallEnvironment]` returned YES when the
`__OSINSTALL_ENVIRONMENT` env var was set, so Terminal.app's sandbox
restrictions were not applied — weaponized via Word-document command
injection to execute code in the Terminal.app context.

Supporting anecdote for the wave-61 design premise (a): **env vars
are attacker-influenced input and must not be authoritative for
security-tier selection.** A real 2026-era sandbox escape pivoted on
exactly that mistake. Our guard's precedence (constructor kwarg >
env; default production) is the structural answer. Watchlist only.
