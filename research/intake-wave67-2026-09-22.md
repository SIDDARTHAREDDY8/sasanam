## What was read

CyClaw's authentication design (a personal AI gateway, stdlib-first Python, comparable threat posture: single-host agent gateway, audit-attribution requirements):

- **Named, per-device, individually revocable bearer tokens** replacing a single shared API key, stored as hashes. Both credential paths (session cookie for browsers, `Authorization: Bearer <token>` for programmatic clients) resolve to a username so "the audit log can attribute every query". Additive over the old shared key — no existing behavior changed (`auth.enabled` default false).
- **Server-side sessions, not stateless signed tokens:** "A stateless signed token cannot be withdrawn before it expires without a revocation list, which is a session table wearing a disguise." Revocation is instant because the authority holds live state.
- **Identity vs authentication, stated explicitly:** "What is missing is identity, not authentication. A single shared secret *is* authentication in the 'something you know' sense. What it cannot do is say *which* machine asked, or let one device be revoked without rotating the credential for every other device."

## Applied learnings (2)

1. **Live revocation state beats stateless tokens.** Our wave-67 tokens are HMAC-verified against the live `ConsumerRegistry` (which holds the revocation set), not self-contained stateless bearer strings — exactly the CyClaw choice. A token whose registry entry is revoked fails closed instantly, no expiry wait. This confirms the "verify at ack time against live registry state" design over any "signed token verified offline" alternative. (Recorded as design rationale in `workstreams/evals/CONSUMER_REGISTRY.md` §(b).)
2. **Named + individually revocable is the attribution primitive.** Our two-registrations-same-consumer-id design (distinct public `token_id`s, independent revocation, records distinguishable in the chain) is the same shape as CyClaw's named per-device tokens — the "which machine asked" answer for evidence, not just "something valid was presented". Confirmed rather than changed: the break-first probe `same_id_two_consumers_distinguished` pins it.

## What was not taken

- Their password/session/CSRF/TLS stack: out of scope for the D5 ack layer (the registry binds *registrations*, the deployment binds registrations to people — stated in the design doc §(d)).
- The mcp-gateway-registry audit-logging doc (also in results): its "per-instance attribution" (`<service>@<instance_id>` subject embedding) is a deployment-identity convention, not evidence-layer mechanism; and its tamper-evidence section is still roadmap — our hash-chained log already exceeds it. No action.
- The bernstein results: HMAC-chained audit + bearer-token task server, consistent with our existing architecture; nothing new for this wave's token design.
