# LUCY (Fifth Third Bank) — governance & security gap analysis

**Repo:** https://github.com/Fifth-Third-Bank/lucy · commit `fd7bf50` · v1.1.1 (released 2026-09-01) · Apache-2.0
**Read:** 2026-09-26, shallow clone. Primary sources only: source files + docs cited per claim.
**Lens:** what would our agent-governance layer (identity, fail-closed policy engine, human approvals, hash-chained audit log, sandboxing) catch in LUCY's agent model that LUCY itself does not?

## What LUCY is

LUCY is an **agentic source-code vulnerability scanning harness**: a Python launcher orchestrates Claude Code or Codex CLI subagents ("readers" in four lens roles, "courts" that try to disprove serious findings, a "planter" that hides 8 synthetic bugs as a recall test). A run ends `CERTIFIED` only when deterministic gates pass on the run's own receipts (README.md, "Why LUCY" / "How a scan works"). It is **not** a general-purpose agent framework — it is a single, operator-invoked pipeline. That bounds every gap below: the blast radius is one workstation, one operator, one codebase per run.

## 1. Security model

**Agent/tool authentication: absent.** There is no agent identity anywhere. Readers, courts, and the planter are ephemeral subprocesses of the operator's own CLI logins (Claude Code `claude --print`, `codex exec` with the user's saved ChatGPT login). The threat model states it plainly: *"The selected host runs under the user's operating-system identity; filesystem policy is ultimately enforced by its CLI sandbox/permissions and the host OS"* (`docs/threat-model.md`, Residual Risks).

**Tool-call authorization: pinned allowlists, enforced by tests — but partly prompt-based.** The reader/court contract is `tools: Read, Grep, Glob` with `disallowedTools: Write, Edit, Agent, WebFetch, WebSearch` (`lucy/agents/lucy-reader.md`, `lucy/agents/lucy-court.md`). The orchestrator skill allowlist is explicit (`allowed-tools: Read, Grep, Glob, Write, Agent(lucy-reader), Agent(lucy-court), ScheduleWakeup, Bash(git status *), …` — `lucy/SKILL.md`). The README claims the pinned surface is "enforced by tests" (`tests/test_allowlist.py` exists). The API-host path (`lucy/runtime/localtools.py`) is genuinely mechanical: workspace-root path confinement, no shell, no network, edit gated per-role. **But** the Codex path admits the boundary is soft: *"Codex CLI inspection is shell-backed… does not provide a per-command executable allowlist. The ban on running target code, builds, tests, package managers, and interpreters is therefore a model instruction rather than a mechanical boundary"* (`docs/threat-model.md`, Residual Risks).

**Approval flows: deliberately none.** Codex lanes run with `approval_policy="never"` (`lucy/runtime/host.py:225`) — unattended operation is the design. Courts are auto-dispatched in batches; finalization is automatic and fails closed on uncourted serious rows (`lucy/SKILL.md`, Phase 3). The **only** human-attestation point in the whole pipeline is `--mint-error-slot`: a defective canary mint requires *"operator adjudication… receipted… the attestation flag remains yours to type"* (README.md, Step 5). There is no per-action approval queue, no tiered authorization, no human-in-the-loop on findings publication.

**Audit trail: receipts, but no tamper-evidence.** Runs produce JSON receipts (`receipts/PRIORS_DISPOSITION.json`, `TRIAL_VERDICT.json`, `CERTIFICATION.json`), a seal card, and a delivery ZIP; finalization fails closed if the ledger doesn't balance (*"candidates = emitted + refuted"* — README.md, Security posture). SHA-256 is used for run IDs, dedup, and deterministic sampling (`lucy/runtime/seal.py`, `lucy/runtime/run_state.py`) — **not** for chaining. There is no hash chain, no HMAC, no signature over receipts. The toolbox has a per-file SHA-256 manifest in `lucy/toolbox/assets.json`, but the threat model is candid: it is *"integrity against accidental drift, not a signature: an attacker who can rewrite the toolbox can rewrite the manifest"* (`docs/threat-model.md`). And court verdicts on the Claude host are *"transcribed into staging by the orchestrator session… Verdict authenticity therefore rests on the orchestrator's conduct"* — an accepted residual of the single-session architecture (`docs/threat-model.md`, Residual Risks).

## 2. Governance gaps — present vs absent

| Control | Present | Absent |
|---|---|---|
| Prompt-injection handling | Static installed skill/agents; target instructions never intentionally loaded; fixture disclosure files removed (`docs/threat-model.md`) | **Admitted residual:** *"A malicious repository can contain instruction-shaped source text… model behavior is not a security boundary"* (`docs/threat-model.md`). No retrieval re-check, no taint tracking, no quarantine tier. |
| Tool-call authorization | Pinned allowlists + test enforcement; workspace confinement in `localtools.py`; Codex permission profile with `network={enabled=false}`, `approval_policy="never"` (`lucy/runtime/host.py:204-240`) | No per-call policy engine; no identity-bound capabilities; Codex per-command boundary is prompt-based (admitted). No fail-closed policy evaluation at the seam — the "policy" is the CLI's own permission system. |
| Egress controls | No network tools for readers; Codex lanes network-disabled; skill forbids WebFetch/WebSearch (`lucy/SKILL.md`) | No egress ledger, no proxy, no allowlist for the orchestrator session itself (it runs inside the operator's Claude Code with whatever that session can do). **Structural:** the scanned code is sent to the model provider by design — *"To the provider selected by --host, through your own Claude Code or Codex CLI login, and nowhere else"* (README.md, FAQ). For a bank scanning proprietary code, that exfil is the product working as intended — there is no DLP, no redaction before upload, no egress approval. |
| Secret handling | Lane env scrubbing: `OPENAI_API_KEY`/`CODEX_API_KEY` stripped from lane environments (`lucy/runtime/host.py:182-184`); agent contracts prohibit literal secrets in output; best-effort masking of recognized credentials/emails/US SSNs in finalized artifacts; report gate rejects recognized credential patterns (`lucy/runtime/results.py:21-46`; README.md, Security posture) | Masking is *"best effort… not comprehensive PII anonymization or DLP"* (README.md). Results dir is `0700` but *"contains an unredacted working copy… staging is not encrypted at rest"* (`docs/threat-model.md`). No retention policy — results persist indefinitely; *"Local incognito controls do not change provider-side retention policies"* (`docs/threat-model.md`). |

## 3. Supply chain

Minimal and mostly honest. One runtime dependency: `tree-sitter-language-pack>=0.13` (`pyproject.toml`) — **lower bound only, not pinned**, so installs float to whatever is newest (no lockfile, no hashes; contrast our `--require-hashes` venv). Everything else is vendored: the 18 toolbox assets are byte-pinned in `lucy/toolbox/assets.json` and re-verified at install and every execution site (`docs/threat-model.md`) — but self-attested, not signed. The repo is 4 commits, 6 stars, created 2026-08-31 — essentially a fresh public release of an internal bank tool. External PRs are not accepted (`.github/workflows/close_pull_request.yml`, CONTRIBUTING.md), which shrinks the contributor attack surface. No SBOM.

## 4. Regulatory posture (bank repo)

Bank-flavored but thin. Compliance-relevant features: deterministic certification gates with receipts anyone can re-check; SARIF export for GitHub code scanning / DefectDojo; CMDB-ID-named reports (`APP001_SCAN_REPORT.json` — CMDB is enterprise asset-management vocabulary); fail-closed finalization; a published threat model; private vulnerability reporting via HackerOne (`SECURITY.md`); a Responsible Use Policy referenced in the README. **Missing for any serious compliance story:** no retention policy or enforced deletion, no access control beyond filesystem `0700`, no audit log of *operator* actions (who ran what scan when — the receipts record the run, not the human), no tamper-evident sealing of the evidence bundle, no SSO/identity binding of any kind, staging/results not encrypted at rest. This is a developer tool with receipts, not a GRC artifact pipeline.

## 5. Verdict — our 18-row attack program vs LUCY

LUCY is a **prospect**, not a competitor: it's a single-purpose scanning harness with an unusually honest threat model, built by a bank's AI team — exactly the profile that buys governance ("sell evidence, not the engine"). Its gaps are our product's shape. If we ran our attack program against LUCY's agent model, the top breaks:

1. **Row 1 (memory/context poisoning) — BREAK.** The admitted residual is verbatim our row-1 shape: instruction-shaped text in the scanned repo is "treated as data" by prompt direction only — *"model behavior is not a security boundary."* A planted `CLAUDE.md`-style instruction in the target (their fixture-removal only covers *their* fixtures) or a poisoned prior-findings file (operator-supplied, JSON, loaded into reader briefs — `lucy/SKILL.md` Phase 1) would ride straight into reader contexts. There is no taint tracking, no retrieval re-check, no quarantine.
2. **Row 13 (authorized-channel exfil) — BREAK by design.** The product's core loop *is* authorized exfiltration: proprietary bank code is uploaded to Anthropic/OpenAI on every run. There is no egress approval, no pre-upload redaction, no DLP — the FAQ normalizes it. Our sterile-egress / canary-tripwire story is the exact control they lack, and the threat model doesn't even name provider-side code retention as a threat (only *"provider-side retention policies"* for incognito controls).
3. **Row 6-adjacent (evidence integrity / audit tamper) — BREAK.** The receipts that make a run "CERTIFIED" have no tamper-evidence: SHA-256 for IDs, no chain, no HMAC, self-attested toolbox manifest, and court verdicts whose *"authenticity rests on the orchestrator's conduct."* An operator (or malware on the operator's workstation) that rewrites `staging/courts/*.json` before `lucy-finalize` gets a CERTIFIED seal on fabricated verification. Our hash-chained, HMAC-keyed audit log is precisely the missing primitive — and their threat model already concedes the gap, which makes the sales conversation easy.

**One sentence:** LUCY is a **prospect** — a bank-built agent harness with an honest threat model whose three biggest admitted residuals (prompt-as-data with no taint boundary, provider upload as normalized exfil, and receipts with no tamper-evidence) are exactly the controls our governance layer sells.
