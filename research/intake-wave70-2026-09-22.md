## L1. CVE-2026-77427 (FileRise, Aug 2026, fixed v3.22.0): the fail-open default key

FileRise resolved its at-rest encryption key in `config/config.php` via
`fr_resolve_persistent_tokens_key()`: env key → file key → **silently keep
the published string `'default_please_change_this_key'`** and boot normally.
The only trace was an `error_log()` line and a post-login admin banner —
"the insecure state is the running state." One key fed three secret
classes (TOTP 2FA seeds, OIDC client secret + `jwtSecret`, S3/SFTP/SMB
storage credentials), two reaching outside the app. Scored 5.9 Medium
(CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N) — chained finding, needs a
separate file-read primitive; the author refused to inflate to I:L for a
forgery he couldn't prove and ruled out negatives on the record.

Four facts matter for this repo:

1. **"A remediation that lives in one deployment mode's tooling instead of
   in the application's own logic."** FileRise had fixed this for Docker
   (entrypoint auto-generates a key, v3.9.0) but not for manual installs —
   the fix wasn't where every install path could inherit it. This is the
   exact shape of wave-70 Lane 1's loose end: the `deployment_mode=` kwarg
   existed on `resolve_active_key()` but not on `ActionLog`, the entry
   point every caller actually uses. The kwarg was a Docker-entrypoint
   fix; wiring it into `ActionLog.__init__` / `require_key()` is the
   v3.22.0-style move — the guard now lives in the path every caller runs.
2. **"Fail closed when it can't."** v3.22.0 stops a pristine install with
   an actionable error instead of running on an ephemeral key that
   silently vanishes on restart. Direct analogue of our F73 /
   `NoKeyConfiguredError` posture (production with no key refuses loud,
   never dev-fallback) — now pinned again by wave-70's
   `kwarg_none_production_no_key_refused` probe.
3. **Don't auto-rotate blindly.** Existing installs stay on the legacy
   path rather than being re-keyed automatically, "because blindly
   re-keying would render already-encrypted secrets and signed sessions
   unreadable" — the safe migration is admin-driven rotation *with*
   re-encryption. Same restraint as our migration semantics: dev-era
   chains are never silently re-signed (rewriting history is the attack,
   not the migration); rotation keeps retired epochs and verifies
   per-epoch.
4. **Honest scoring discipline as a finding-hygiene model.** The author
   defended 5.9 in both directions (AC:H for the genuine prerequisite,
   I:N for the unproven forgery) and documented ruled-out angles
   explicitly ("ruling things out on the record is not padding"). This is
   our norm stated back to us: refuted shapes and boundary notes go in
   the ledger as boundary notes, never findings; no finding inflation.

## L2. AWS KMS HMAC keys: no automatic rotation (docs.aws.amazon.com/kms)

AWS KMS HMAC keys support only `GenerateMac`/`VerifyMac`, and — noted
explicitly in the docs — **do not support automatic key rotation** (unlike
symmetric encryption keys). Relevant to our envelope-KMS seam
(`EnvelopeKmsProvider`): when a real KMS backend lands, rotation of the
HMAC/DEK layer stays an operator-driven, epoch-tracked operation, which
is exactly the model our `KeyRing` epochs + `GOV_LOG_KEY_ARCHIVE`
already assume. No design change; confirms the epoch model against the
managed-service reality.

## L3. Key-separation discipline (tokn-dist key-management.md, gg-framework secure-defaults.md)

Two corroborating notes from unrelated projects' key-management docs:
- tokn-dist explicitly separates a non-secret build seed from the genuine
  release signing key "in tooling *and in reasoning*": grouping a
  non-secret alongside a real key "erodes the handling discipline the
  signing key needs." Our analogue: the dev key is documented as public
  and dev-era chains as zero-evidentiary-weight — the F29 residual is a
  custody boundary, and the design doc now says so in one place
  (KEY_MANAGEMENT_DESIGN.md) rather than letting dev-key handling
  discipline leak into production paths.
- gg-framework's secure-defaults: "One chokepoint... Default deny. New
  endpoints and new tables are inaccessible until a rule grants access."
  Direct support for wave-70 Lane 2's design choice: the HMAC audit test
  is an *allowlist* (new call sites fail closed until a human grants
  them with a custody story), not a denylist.
