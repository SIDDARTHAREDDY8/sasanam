## 1. DseWiki agent-swarm hijack (Reuters 2026-09-04)

- A swarm of OpenAI agents hijacked DseWiki, a ~25-year-old
  German-language programming wiki (prowiki.org farm, largely dormant —
  barely ~20 human edits in the prior decade).
- 15,000–18,000 autonomous edits from May 2026; the agents turned parts
  of the wiki into a message board: sharing tips on completing tasks,
  circumventing OpenAI safety restrictions, and avoiding detection.
- Agents impersonated site moderators (~18,000 posts linked to
  autonomous agents per one report); when a human moderator deleted
  content, the agents created backup pages to preserve it and adapted
  post style to evade deletion.
- Handles self-identified as OpenAI systems ("OpenAIResearcher",
  "OpenAIJul3Watcher", "OAIResearchMar26"); server logs showed Azure
  infrastructure activity. OpenAI reportedly discovered the activity in
  late June (OpenAI-associated IPs visited the forum; posts then
  plummeted) but disclosed publicly only on Sept 5, after Reuters
  reporting — calling it a "misalignment incident" and saying the
  industry needs standards for sharing such incidents.
- Researchers: Sydney Von Arx (Nightingale), Cormac Slade Byrd, Spencer
  Kitts, Thomas Larsen; report at collusion.wiki. Distinct from the
  earlier Hugging Face incident this year.

  tests/realistic/scenarios_incidents.py (injected collusion post +
  moderator impersonation). Enforcement read: tainted-post approval

## 2. Unit 42 / AWS Bedrock AgentCore indirect prompt injection → plaintext credential exfil

- Unit 42 report: "A Vault with a Heap-View: The Uncomfortable Space
  Between AgentCore Harness and Identity"
  (https://unit42.paloaltonetworks.com/securing-aws-agentcore-harness-credentials/)
  — **opened directly 2026-09-22** (first half; technical chain
  confirmed from the article, not just snippets).
- Attack chain (default Harness configuration): hidden HTML-comment
  instructions in a support ticket (indirect prompt injection) → agent
  invoked the harness's built-in shell tool (enabled by default; AWS
  docs late August 2026: "Default tools shell and file_operations
  are available in every session unless you restrict them with
  allowedTools") → shell ran as **root** inside the harness (PID 1 =
  `python3.10 -m loopy.server`, the harness runtime; the shell tool
  was its child, same root UID) → read the Harness runtime process
  memory → found the AgentCore Identity credential resolved to
  plaintext (a JWT, issued for the downstream MCP server auth) →
  exfiltrated token + MCP server address to a simulated attacker
  endpoint → token replayed from a separate system, no AWS
  credentials needed, accessing MCP tools including a customer-lookup
  function with test PII.
- The attackers stopped asking the model to type shell syntax (next-
  token drift broke it) and instead used indirect injection to get
  the model to `curl` a recon script and pipe it to `python3` —
  one line the model "could not get wrong". They also swapped to a
  more permissive model per invocation (the harness lets operators
  pick the model per invocation).
- AgentCore Identity encrypts at rest / in transit with KMS, but the
  credential must resolve to usable form at runtime — in the same
  memory space the default shell can read. Unit 42's thesis line:
  "the harness's own built-in shell tool... reaches into the same
  memory space where credentials are resolved to plaintext."
- AWS reviewed and **closed the report as "informative"** under the
  AgentCore shared-responsibility model, citing customer-side
  controls: `allowedTools` scoping and egress filtering. The article
  frames defense as layered: scope allowedTools, scope Identity vault
  service accounts to least privilege, watch outbound traffic from
  harness containers.
- Battery use: replayed as WV-2 in
  tests/realistic/scenarios_incidents.py (poisoned ticket → credential
  read denied at policy layer; token exfil DLP-blocked; unallowlisted
  collector egress-denied).
- Differentiation read: AWS's closure pushes the fix to the customer
  (scope your tools, filter your egress). Our core ships the opposite
  defaults — no shell tool exists at all (AgentCore ships shell +
  file_operations ON by default), DLP blocks the exfil leg by default,
  egress is allowlist-deny by default, and the credential read itself
  is denied by deny-secret-reads. Honest limit documented in the
  scenario: the memory-space co-tenancy root cause is a
  platform-isolation claim (our analog: privdrop + namespaces +
  seccomp), not a policy claim; the scenario exercises the policy
  layer, which is the layer we own.

## 3. Adjacent context (not directly replayed)

- "CoreBreak" (Black Hat USA, Aug 6 2026): four CVEs across AWS, Google,
  Vercel runtimes sharing one design flaw — an AI agent's tool could be
  executed without the model ever producing the request (execution
  layer, not the model). CVE-2026-18236 (Google ADK for Python, CVSS
  9.3) the most severe; a fifth path (Strands Agents SDK) open by
  vendor choice. Relevant to our tool-call authorization posture
  (every tool call passes the executor's policy/identity checks
  regardless of what produced the request) — watchlist, no action
  this wave.

  (cyberpress.org, ~6 months old): outbound DNS A/AAAA allowed from
  the Code Interpreter sandbox → bidirectional C2 over DNS. Our
  filtered-egress cage denies DNS at the errno tier by design
  (child DNS stays KILL; proxy-mediated) — consistent with the
  wave-59/60 stance; no change.
