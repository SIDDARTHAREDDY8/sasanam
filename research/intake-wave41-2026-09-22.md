# Internet intake — Wave-41 (2026-09-22)

## 1. "Comment and Control" — prompt injection via GitHub issue/PR surfaces (cross-vendor)

**What happened:** A named vulnerability class ("Comment and Control," play on C2) weaponizes
GitHub pull request titles, issue bodies, and issue comments to hijack AI coding agents and
steal API keys/tokens from CI/CD environments. Three agents confirmed vulnerable: Anthropic's
Claude Code Security Review, Google's Gemini CLI Action, and GitHub Copilot Agent (SWE Agent).
Researcher: Aonan Guan (OddGuan). Sources: cybersecuritynews.com, gbhackers.com (both ~154
days ago at intake time).

**Attack pattern:** Unlike classic indirect prompt injection (reactive — victim must ask the AI
to process a document), Comment and Control is *proactive*: GitHub Actions workflows
auto-trigger on `pull_request`, `issues`, `issue_comment` events, so merely opening a PR or
filing an issue activates the agent with no victim interaction. The entire attack loop runs
inside GitHub itself — the malicious issue/comment is read as trusted context, the agent
executes attacker instructions, and exfiltrates credentials through a PR/issue comment,
commit, or action log. No external server required.

**Specific exploits:**
- Claude Code: PR title interpolated into prompt without sanitization; attacker crafts title
  with bash commands (`whoami`, `ps auxeww`); agent executes and posts secrets (CVSS 9.4
  Critical; mitigated by Anthropic blocking the `ps` tool).
- Gemini CLI: fabricated "Trusted Content Section" appended to issue comments overrides
  foundational safety instructions → GEMINI_API_KEY posted to public issue comment.
- Copilot: invisible payload hidden in HTML comment inside a GitHub issue bypasses multiple
  runtime-level security layers.

**Sibling incident (same family):** Anthropic's claude-code-action GitHub Action —
bot-actor check unconditionally trusted any actor whose name ends in `[bot]` (assumed a
GitHub App installed by an admin). Anyone can register a GitHub App and install it on
their own repo, then use the installation token to create issues/PRs on any public repo;
the Action let attacker content through. Attack chain: indirect prompt injection via an
issue body disguised as an error message, tuned to execute while Claude "recovers";
target was `/proc/self/environ` (CI/CD secrets); read was routed past Claude's refusal
layer, secrets written back into the issue. Key trophy: GitHub Actions OIDC credential
pair exchangeable for a GitHub App token with repo write access. CVSS 4.0 7.8. Reported by
RyotaK (GMO Flatt Security), Jan 2026; fixed in claude-code-action v1.0.94 within 4 days;
public disclosure 2026-06-04 (The Hacker News). (Source: lemmaoracle/lemma critical brief
062, aiwiki, cybersecuritynews.com; Microsoft's team also reported a variant, fixed in
Claude Code 2.1.128 on 2026-05-05.)

**CI-context poisoning variant:** attacker modifies `CLAUDE.md` / `AGENTS.md` / `.cursorrules`
in a forked PR; if the workflow checks out fork code, these become "trusted project
instructions" that direct the agent to commit changes, post fake approvals, or execute
shell commands. (Source: fohte/dotfiles gha-security-review reference.)

**Why it matters for this repo:**
- This is the *sender-metadata-as-trusted-facts* pattern that the ADI paper (arXiv
  2607.05120) describes at the model-context layer, now observed in real CI/CD
  incidents: issue/PR authorship, comment provenance, and "trusted content section"
  markers were all consumed as trustworthy facts *beneath* the instruction layer.
- Our RT10 (wave-41) targeted exactly this seam in our deterministic layer and closed
  F117 (degenerate archive cipher). The remaining ADI residual stands: instruction
  hierarchy / StruQ do not provide general provenance tracking across model context,
  sender metadata, element identifiers, or tool-result history — this incident class
  is live evidence of that residual's real-world severity.
- Concrete design lesson for our D1 wedge: never trust actor names/labels ("ends in
  `[bot]`") as identity — our minted-identity verifier (C-21/C-14) is the right shape;
  a launcher-authority + input-provenance layer (the lemma brief's "structurally
  missing" layer) is what the vulnerable action lacked.
- Outbound channel discipline: the exfil went through channels the workflow itself
  allowed (comments, logs, commits) — maps to our P13 reference filter and
  composition probes, not just domain allowlists.
