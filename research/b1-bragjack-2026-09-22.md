# B1 watchlist analysis: BragJack — privileged-channel hijack below the policy layer

Filed wave-45 as a B1 watchlist entry (new incident class). Analyzed
wave-46 (2026-09-22). **Verdict: RETIRE — the class does not bite the
executor-layer controls.** No finding filed. One forensics residual
documented below (deployment note, not a finding).

## The class, precisely

BragJack (Gal Weizman / Forever Security, Sept 2026; CVE-2026-0628
CVSS 8.8 on Gemini, CVE-2026-55945 on Edge): a malicious **browser
extension** injects commands into the trusted communication channel
between an AI browser assistant and its privileged "body" components —
**below the model layer**. Dubbed "prompt forcing": the commands never
pass through the model's safety filters because they never pass
through the model at all. This is not prompt injection (no model
trickery); it is **channel hijack against the privileged control
plane**. The report's lesson, verbatim in spirit: AI agents need strict
origin validation and isolated command channels.

The structural question for us: our instruction-hierarchy / StruQ
controls (`gov/adapters/trust.py`) sit *above* the executor — they
classify model-layer content. Is there anything that can inject tool
calls *below* that layer, into our privileged control plane, the way
the extension injected into the browser agent's?

## Where our "body channel" is

Model output → `run_tool_loop` (parses tool calls, StruQ channel
separation) → `GovernedBinding.call` → `ToolExecutor.call(identity,
tool, **args)` → policy, DLP, identity check, approvals, sandbox,
tamper-evident audit log. The privileged control plane is the
binding→executor→tool-implementation path.

Break-first demonstration (scratch
`~/workspace/agent-governance-demo/scratch/w46_bragjack_breakfirst.py`,
run against the gov-venv):

1. **Sub-loop dispatch is real.** A non-model in-process origin holding
   the facade + a minted identity can dispatch `facade.call(...)`
   with no assistant message and no `run_tool_loop` turn. It executes.
2. **But the executor layer is dispatch-path-independent.** The same
   sub-loop dispatch of an exfil-shaped `api_call` is DENIED by the
   executor's policy/DLP stack — every control below the trust
   adapter (identity verification, policy, DLP, rate guards,
   approvals, sandbox, ledger, audit) applies identically however the
   call was dispatched. BragJack's impact came from the *absence* of
   controls at the body layer; our body layer carries the full stack
   regardless of how a call arrives.
3. **Origin validation — the incident's lesson — is present.** A
   forged, non-minted identity is refused fail-closed
   (`UnmintedIdentityError`); `_check_identity` runs on every
   `executor.call`; the approval queue re-verifies identity at
   execution time (F42) and never trusts `action["identity"]`; bridge
   ingress authenticates identities in-process. There is **no
   unprotected cross-boundary channel** analogous to Gemini's: an
   extension-analogue *outside* the process has no IPC to speak on.
   (The approval web UI is the network surface, but driving it is an
   operator-session class, not this one — out of scope here.)

## Why the trust adapter being bypassed is not a miss

The trust adapter was never the executor's authorization mechanism;
it is a content-classification layer at the model boundary. A
sub-adapter injector bypasses StruQ tags and privilege-claim
quarantine — exactly as BragJack bypassed model safety — and still
faces the executor's authorization stack. The hierarchy defenses
(F79–F121) are intact at their layer; this class attacks a different
layer and finds it guarded.

## The honest residual (deployment note, not a finding)

Sub-loop dispatch is **unattributable in the audit log**: the
demonstration shows the sub-loop call audits with identical
provenance (`agent_direct`) and identical identity fields to a
model-loop call — forensics cannot distinguish "the model authorized
this" from "an in-process component dispatched this". There is no
per-call model-intent attestation.

This is bounded by the documented trust model, not a control gap:
in-process code is the trusted computing base (F31 facade docstring
declares in-process introspection out of scope; the harness warning
is explicit that without a deployment-controlled PrincipalRegistry,
minting is self-asserted — any in-process code can mint). The product
does not claim "every tool call is cryptographically bound to a model
utterance", so there is no gap against a claimed control. Filing a
finding for an explicitly out-of-scope residual would be
finding-theater; the wave-45 swarm analysis set the precedent
(deployment notes, not findings).

Deployment guidance: do not host untrusted third-party components
(plugins, extensions — the actual BragJack habitat) in the harness
process. Untrusted components belong behind the bridge boundary,
where records are foreign-executed, MAC-bound, and never
sweep-executed by our executor (D1/`queue_external`, T12/F85).

A possible future forensics improvement — stamping the originating
assistant message's hash through `run_tool_loop` into the tool_call
entry so direct dispatches log a distinct `direct_dispatch`
provenance — is noted but not pursued: it improves forensics, it does
not close an authorization gap, and the in-process boundary remains
the trust line.

## Bottom line

BragJack is a real incident class, and the analysis was worth doing:
it forced the question "can anything inject tool calls below the
trust adapter?" The answer is yes, mechanically — and it doesn't
matter for authorization, because the executor layer validates origin
and enforces policy independently of dispatch path. The class is
retired from the B1 watchlist. The remaining watchlist entry is
reputation-mediated skill injection (Moltbook/Sybil — no marketplace
surface exists in-repo).
