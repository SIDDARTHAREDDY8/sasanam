## (a) CVE-2026-73548 — Envoy extended-CONNECT HTTP/2 request smuggling (FETCHED)

Page opened and read:
https://www.thehackerwire.com/vulnerability/CVE-2026-73548/
(fetched 2026-09-22; page shows "New CVE Received Sep 21, 2026 20:17").

Confirmed from the fetched page: Envoy < 1.36.10 / 1.37.6 / 1.38.4 /
1.39.1 forwarded data for a configured non-WebSocket HTTP upgrade
*before* the upstream accepted the upgrade; an unauthenticated HTTP/2
client could place a complete HTTP/1.1 request inside extended-CONNECT
data; Envoy downgraded it, wrote it unframed to a keep-alive HTTP/1.1
upstream, and returned the socket to the shared pool with the smuggled
response still queued — a different downstream client could then receive
the attacker's response (CWE-444, CVSS 7.5 High). The page's scope note:
"webSocket upgrades, plain CONNECT, disabled backend keep-alive,
per-downstream pools, and max_requests_per_connection set to 1 are not
affected by the demonstrated path." Fixed in 1.36.10 / 1.37.6 / 1.38.4 /
1.39.1. The page links (not fetched) the upstream advisory
GHSA-3vhp-c83q-jqc2 and four fix commits.

**Relevance to our F81 proxy: the class is structurally absent.**
The bug needs three ingredients — HTTP/2 extended CONNECT, upgrade
downgrading, and shared keep-alive upstream connection pooling. Our
`gov/egress_proxy.py` has none of them: CONNECT-only over a plain
client socket, no upgrade handling, no HTTP/2, no connection pooling
(one upstream socket per allowed CONNECT, closed after relay). The
fetched page's own scope note ("plain CONNECT … not affected by the
demonstrated path") confirms the boundary. No new probe warranted —
but the *lesson* is recorded for the implementing wave: if the proxy
ever gains connection reuse or protocol upgrades, this CVE becomes the
first regression test. (Boundary note, not a finding: no
independently-reachable miss in our code.)

## (c) Seccomp arg-filter limitation (Lane-2 context) — CORRECTED

No new technique surfaced. The intake's earlier framing ("TOCTOU on the
sockaddr pointer") was WRONG and has been corrected in
`F81_SECCOMP_PROFILE_DRAFT.md`: classic seccomp BPF cannot dereference
the userspace `sockaddr *` AT ALL — it can only see the syscall's
scalar registers. This is an inability, not a race; there is no
"advisory-only" middle ground for a `connect()` destination rule
because no such rule can exist in classic BPF. Scalar `socket()`
domain/type filtering is race-free and stands; destination confinement
belongs to netns + proxy + firewall.
