## L1. The bytearray design, corroborated twice

- sota-skills cryptography rules (martinholovsky/sota-skills,
  `skills/sota-code-security/rules/04-cryptography.md`): "Key material
  in memory: avoid copies (immutable strings in GC languages spread
  copies — prefer byte arrays you can zero)".
- Karl Knechtel (discuss.python.org): "Python strings are immutable at
  the Python level... If you need this level of control over memory,
  you will need to use some kind of mutable buffer type... `bytearray`
  is the most obvious choice for this. Then you would need to arrange
  a way to make sure the buffer is consistently zeroed out before
  being garbage-collected."

Applied: this is exactly the wave-71 mechanism — `KeyMaterial.key`
moved to `bytearray` storage, `zeroize()` + `destroy()` wipe before
the buffer is dropped. The `zeroize()` fail-loud refusal of
`bytes`/`str` is the codebase enforcing Knechtel's immutability point
as a TypeError instead of prose.

## L2. The honest boundary, stated back by the language's own forum

Knechtel again: "if your program is still using the 'string' at the
time that the memory dump is created, there is nothing that could be
done about it in Python, *or any other programming language*...
If you have access to the data, you have access to the data."

Applied: this is the wave-71 honesty ledger's item 2, now with
independent corroboration — long-lived process keys (env/file
backends must hold the key for the process's appending lifetime)
cannot be protected against a dump taken while in use, in ANY
language. Our residual documentation is not Python defeatism; it is
the industry-acknowledged floor.

## L3. The real fix, named by a practitioner

Barry Scott (same thread): sensitive data can also reach the swap
file; "There are APIs to allocate memory that is never written to
swap/page files. But these are only usable at the C level... You
might be able to write a C extension to do this so long as the
sensitive data is never given to python, as it will then be leaked."

Applied: confirms the design doc's item 5 — the real fix for the
raw-memory threat model is a C-extension locked-memory backend (or
HSM/offload), deployment-owned. The openSUSE secure-coding checklist
(result 2) adds the adjacent partial mitigations: `mlock()` against
swap, `setrlimit()` against core dumps — both core-dump/swap-only,
both C-level, both recorded as future deployment-owned hardening,
not this wave (partial fixes claimed as the fix would be theater).

## L4. Adjacent pattern worth noting, not adopting

`zeroizepy` (Medium, Jan 2026): a `CryptoKey` with `.destroy()`
raising on post-destruction use, plus context-manager auto-destroy
on exceptions — the same two disciplines wave-71 ships
(`destroy()` fail-loud, `key_buffer` finally-wipe). Convergent design;
no dependency taken ($0/local constraint holds — ours is ~60 lines
with no new deps).
